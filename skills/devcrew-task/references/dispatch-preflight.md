# Dispatch preflight

Use for every AGENT EXECUTION task after classification. The dispatch message is sufficient as a brief when no separate accepted plan exists; a separate brief skill or document is not required. The phase-manifest, task-checkout, `COMMITTED`, and `capacity-report` procedures below apply to **formal schema-v2** AGENT EXECUTION. Ordinary current-chat tasks instead use their separate persisted accepted plan, ordinary receipts and no-commit candidate lifecycle; do not impose formal source-bind, manifest, commit or capacity-report fields on them.

- Confirm both role configuration and actual runtime dispatch availability before dependent work. Record `ROLE_FILE_EXISTS` and `ROLE_RUNTIME_AVAILABLE` separately. A custom role TOML in a project or subproject is not evidence that the active runtime loaded or can invoke it, especially when the task is opened from a root workspace. Check the active runtime's exposed role/tool capabilities. If the custom role is not runtime-available, a generic agent is a valid fallback only when it can be spawned in a distinct context and receives the exact role contract; record that fallback. If no such context can be created, return `AGENT_RUNTIME_REQUIRED` with `MISSING_CAPABILITY` and `BLOCKED_STAGE`; never substitute the host.
- After successful automatic project sync, continue the same user task and preserve its original request, scope, and acceptance; never ask the user to repeat it. `RUNTIME_RESTART_RECOMMENDED` does not itself block the current task: when the new typed role is not loaded, read its current contract from the DevCrew plugin and use the generic path through the routed spawn builder. Supply `PROJECT_ROOT`, the exact owned scope and acceptance, original user request, and freshly resolved explicit `model` and `reasoning_effort`. Stop only if the separate generic context or required model route cannot be guaranteed. Do not ask the user to approve safe sync: it updates ignored local runtime files and the root ignore rule without staging or creating a Git commit. This permission does not authorize implementation commits for the task.
- `HOST_PROJECT_ROOT` owns DevCrew integration, roles, routing, synchronization, and checks state. Sync and preflight that host once. A task worktree is execution state only: task-local role files and sync are not prerequisites. Generic dispatch receives the exact role contract, explicit model/effort, `PROJECT_ROOT`, `TASK_WORKTREE_ROOT`, `TASK_ID`, owned scope, acceptance, and verification.
- Resolve and record the independent model route using [model routing](model-routing.md) and the runtime capability snapshot. A selected model must appear explicitly as `model` and the selected effort as `reasoning_effort` in every spawn payload, including reviewer and replacement contexts. Keep the full route record and compact selection reason with the brief.
- Before any actual **formal** spawn, load the current applicable [engineering requirements](engineering-requirements.md) and call the context helper's payload builder to derive the envelope at canonical issuance. Planner routes with a nonempty registry require explicit declared `requirements_scope`; executor/reviewer and replacement scopes come from the persisted phase. Validate the complete returned payload. Every runnable formal DevCrew builder call requires host project, task ID, and the exact role identity before it can return: planner uses original `BASE_SHA`; executor uses `PHASE_ID`, `BASE_SHA`, `WRITER_CYCLE`, and repair `REJECTED_CANDIDATE_SHA`; reviewer uses exact `PHASE_ID`, `BASE_SHA`, and `TARGET_SHA`. Reviewer builders also require the exact formal `review-start` contract and bounded verification evidence references, and include both with all three identity values in the final payload. The builder issues the final route and payload before returning; only the private executor payload pipeline may build an unissued intermediate, which it issues after its final message mutation. Keep the complete prepared object, including route, dispatch, issuance ID and payload digest, for postflight. `reviewer_spawn` returns that complete prepared object. Record `SPAWN_MODE` and `SPAWN_REASON`, then use its `spawn.agent_type`, `spawn.model` and `spawn.reasoning_effort` directly in the runtime call. Do not attempt a conflicting typed role first or create a probe agent. Typed mode requires an exact model/effort match or proven override support for that specific loaded role. Generic tool model/effort fields alone do not prove typed-role override support; record `roles[agent_type].supports_overrides=true` only from an explicit role-specific runtime guarantee. Unknown support with conflicting pins selects generic immediately, with the exact role contract and explicit model/effort; unavailable generic fallback stops with `AGENT_RUNTIME_REQUIRED`. A historical local executor override must not substitute for the selected route. After actual dispatch, record effective configuration separately; a payload alone is not applied-route evidence.
- Direct `spawn_agent` or collaboration spawns are forbidden inside the formal DevCrew workflow contract. Every formal actual agent call must use the prepared routed payload and receive a `ROUTE_ID`; after the runtime responds, report the observed `AGENT_ID`, `FORK_TURNS`, task/phase identity, and exact prepared route/dispatch through `capacity-report`. An ordinary lifecycle uses its separate routed payload and ordinary spawn receipt, which binds the same model/effort/fork/payload properties without a phase identity. A spawn without its lifecycle's matching persisted receipt is a routing deviation and cannot satisfy a gate.
- Before implementation, require executor-agent dispatch and the ability to create a separate reviewer context after checks. Require decision/planner dispatch when the plan is missing or materially insufficient, or for bounded validation of an external ready plan without an existing validated phase manifest and matching persisted planner receipt. If any required stage cannot be dispatched, stop before that stage with `AGENT_RUNTIME_REQUIRED`.
- For **formal schema-v2** work, follow [plan selection](implementation-strategy.md#plan-selection): validate an existing plan for current project/API facts, confirmed acceptance and scope, no material unresolved decisions, bounded executor steps, and verification requirements. Only an existing validated phase manifest with a matching persisted planner receipt may skip a new planner dispatch: send it directly to executor for `CURRENT_PHASE` when its lifecycle permits execution. An external ready plan without that manifest requires bounded planner validation, not planning from scratch; reuse its content and evidence, and do not repeat research without a concrete gap. Formal planner output has `TASK_ID`, `TASK_MODE` (`SINGLE_PHASE` or `MULTI_PHASE`) and semantic `PHASES`; even a single capability has one formal phase. Initialize the host-state manifest with `phase init --spawn-receipt-id ID` only when it does not already exist; initialization is create-only and the receipt must match the planner route, task and original base SHA. Validate the manifest against a fresh `task-checkout resolve` receipt before writer dispatch. Planner scopes must use normalized repository-relative paths; aliases such as `./file`, repeated separators, and `..` segments fail validation. Resume rechecks the persisted planner receipt. If the manifest is missing after initialization or does not match task/worktree identity, stop with `PHASE_MANIFEST_REQUIRED` or the machine-readable validation error; never recreate an invalid existing manifest to bypass the error. Before init, each phase must bind every ordered verification item to exact argv (and required timeout/idle-timeout parameters) in `verification_bindings`, derived from project rules and the accepted plan. The host freezes these bindings before execution; executor results cannot select replacement commands. Do not repeat planning without a concrete gap. DIRECT and ordinary no-commit work do not require a phase manifest.
- Every role transition is a new coordinator dispatch with a role-matched contract. Scouts/analysts return findings and cannot promote themselves; decision/planner returns `PLAN_READY` and stops. The coordinator dispatches a separate executor for only `CURRENT_PHASE`, with that phase's goal, scope, acceptance, verification, known contracts and do-not-change constraints. Do not include later-phase acceptance or task-wide implementation instructions as writer assignment. In AGENT EXECUTION, the host does not implement production code. The executor implements within the phase and does not redesign seams, domain models, or confirmed contracts; route `PLAN_INSUFFICIENT` or scope expansion through the technical replan protocol.
- Every independent executor phase requires an observed actual spawn with `FORK_TURNS=none`; `phase advance` does not authorize the old executor. Dispatch receipt recording and verification reject an executor identity already recorded for another phase. A same-phase repair followup may keep its executor only after observed `FOLLOWUP_SUCCESS` and `record_executor_continuation` with the origin receipt, current `WRITER_CYCLE`, exact `REJECTED_CANDIDATE_SHA`, and unchanged issued route/payload. The linked continuation is not a new spawn and cannot satisfy another phase's freshness requirement. These helpers enforce receipt authority; they cannot intercept arbitrary host followups, prove observations the host does not report, or infer activity outside retained task receipts.
- A phase reviewer must follow a formal `review-start` for a `COMMITTED` candidate, receive only its bounded `BASE_SHA..TARGET_SHA` contract and verification evidence, and spawn in a fresh context (`fork_turns="none"`). The report must name the matching `SPAWN_RECEIPT_ID` and `AGENT_ID`; direct, inherited-history, stale-target, or unrouted PASS reports are advisory only and cannot accept the phase.

- Write the brief before dispatch: objective, inputs, explicit file ownership, forbidden scope, acceptance checks, reporting format, and fallback recipient for questions. For large tasks, validate the planner result or reused current brief against all five points of [the short brief contract](implementation-strategy.md#short-brief-for-large-tasks), including the main user/system scenario and acceptance tests/checks. Missing or stale points go back to the planner before writer dispatch; a complete current brief needs no repeated planning, separate `devcrew-brief` invocation, or additional document. Keep phase ownership bounded when referencing task-wide context. Include the task classification, verification strategy and accessible paths to the applicable short brief contract and shared [engineering policy](engineering-policy.md); supply their applicable requirements directly if the worker cannot read them.
- Keep one writer per checkout. Only explicitly user-authorized parallel independent writers use distinct worktrees; otherwise serialize writers. Dependent slices use sequential waves with a barrier.
- Before task dispatch, apply [task checkout policy](checkout-policy.md). Prepare the current working directory with `python3 scripts/devcrew.py task-checkout create --project PROJECT_ROOT --task-id TASK_ID`. Worktrees require the user's actual explicit instruction in `--worktree-request TEXT`; neither AGENT EXECUTION nor delegation authorizes them. In current-directory mode BASE_SHA is the current HEAD: keep an existing working branch, or automatically branch from the primary checkout without changing its tree or index. Dirty state alone does not block registration. Only explicitly requested linked worktrees use the local primary head. Creation never resumes a checkout. Resolve a fresh receipt with `task-checkout resolve`, load the host phase manifest, and validate task/checkout identity. Build initial and replacement payloads through `routed_task_spawn`; it marks writer dispatch durably. The executor receives only the `CURRENT_PHASE` contract. All sequential phases share the same assigned checkout. In default mode `TASK_WORKTREE_ROOT == PROJECT_ROOT`; in authorized worktree mode it is the linked checkout. A replacement handoff resolves the saved mode and must not create a new worktree. Missing authorized worktrees are recreated only with durable explicit authorization and the lifecycle's clean-state proof; unsafe state fails closed without global pruning. Phase payloads use manifest-owned scope, acceptance and verification; task-wide narrative is not write authority.
- `READY_FOR_CLOSE` stops before review and does not represent `ACCEPTED`. Record it only with the current executor's `--spawn-receipt-id ID` and one or more repeatable `--evidence-record PATH` arguments naming host `run-check` records. Initial work uses writer cycle zero; repair work must match the current local-fix cycle and rejected candidate SHA. The phase command verifies each evidence record against the host project, task ID, and task execution root, checks the record/log digest, and stores normalized host-relative references. `phase candidate-commit` revalidates the persisted executor receipt and binds the required verification commands to the exact candidate tree before creating an immutable commit whose sole parent is the phase base. It freezes the writer boundary.
- After commit, `phase review-start --phase-id CURRENT_PHASE` validates the candidate commit, clean branch/HEAD, tree, and bound evidence, then returns a reviewer contract with exact `TASK_ID`, `PHASE_ID`, `BASE_SHA`, `TARGET_SHA`, acceptance, verification, scope, and context. Dispatch a separate read-only reviewer for only `BASE_SHA..TARGET_SHA`. Do not dispatch an executor or planner while status is `COMMITTED` or `REVIEWING`. Submit the exact report through `phase review-report --report HOST_REPORT.json`: exact identity fields plus `VERDICT` (`PASS` or `FAIL`) and `FINDINGS`. PASS requires an empty blocking findings array. Ordinary and phase review reports also accept optional `ADVISORIES`, a list of objects with a nonempty `SUMMARY` and a nonempty `EVIDENCE` array of references. Advisories are preserved for the reviewed candidate and do not affect acceptance or recovery routing. Reports without this field remain valid. Each FAIL finding retains `CLASSIFICATION`, `SUMMARY`, and nonempty `EVIDENCE`; classifications are `LOCAL_FIX`, `SYSTEMIC_REPLAN`, or `OWNER_DECISION_REQUIRED`. These findings halt work without automatic repair. The host stores the normalized report reference and digest; resume and acceptance reread its bytes and fail closed if missing or changed. Capacity rejection leaves the candidate and `REVIEWING` state intact; resume requests review of the same target SHA.
- A PASS report is not acceptance by itself. `phase accept --phase-id ID` revalidates the host report digest and identity, candidate commit/tree, branch/HEAD, clean writer boundary, and bound verification evidence before recording the immutable `ACCEPTED_SHA`. Then `phase advance --phase-id NEXT` explicitly unlocks the next sequential phase. Every declared dependency must be `ACCEPTED`; the next phase's immutable base is always the immediately preceding accepted phase SHA so the linear task branch advances without rewriting accepted commits. Before any later-phase resume, dispatch, writer routing, or advance, recheck the full accepted predecessor chain, including each Git commit object and trailers, evidence, and host report bytes/digest/identity/PASS. Require a clean task checkout at the accepted boundary before writer dispatch. If scope or requirements change, request replan rather than expanding a phase silently.
- Normalize every owned path and reject absolute, outside-repository, glob, duplicate, or same-wave conflicting ownership before dispatch.
- Stop a dependent wave when any expected slice is missing, failed, or reports unresolved problems. Integrate independent work before final checks.
- Use recorded execution evidence for checks. A stated command, role claim, or partial log is not proof of execution.
- Run task commands with `--project HOST_PROJECT_ROOT --execution-root TASK_WORKTREE_ROOT --task-id TASK_ID`. Check logs and receipts stay under host checks state; command cwd, Git HEAD, and fingerprints come from the task execution root. Verify and reuse those receipts with the same expected execution root and task ID. Omitting the execution-root options retains legacy single-root behavior.

The host runtime, not DevCrew Python, performs `spawn_agent` and observes its
result. Keep the resolved route and dispatch with the host call so an explicit
postflight report can record the result. Do not probe alternate roles, change
model/effort, or automatically retry after a host runtime rejection.

Before a writing slice, also verify:

1. The checkout/branch/HEAD are the intended ones. Record existing user edits. For same-root work, capture `capture-state --project PATH --include-files`; for task worktrees, use the host as `--project` and the task checkout as `--execution-root`. Keep the JSON and an explicit JSON array of owned paths in host checks state.
2. The accepted plan cites verified APIs/guarantees and relevant producer/consumer or analogous evidence. The coordinator checks that evidence is available and the plan is grounded; substantive investigation belongs to the assigned research/planning role, not a second host investigation. State the invariant and observable test rather than prescribing an unverified fix.
3. Ownership covers necessary callers, tests, configuration and migrations. Compare the plan with symbol references and the compiler/test output where applicable. A missing file is a reason to revise the map, not permission for the worker to expand it.
4. Forbidden scope does not forbid a required acceptance step. Describe expected inputs and outputs at each inter-slice boundary; dependent slices receive real integrated interfaces.
5. The worker can access every required tool, fixture and system. Do not ask a reader role to run tests or an isolated worker to measure an unavailable service. State which other checks cover adjacent areas and how the result will be used.
6. Give precise paths and relevant section/line ranges, with shared invariants included. Refresh ranges after editing documents. Avoid sending the entire design when the assigned slice needs only part of it.

For AGENT EXECUTION, the coordinator's preflight is limited to routing and checking the plan's sufficiency. It does not perform the substantive investigation or decide a material design issue. Missing product/owner requirements require a focused user question before dependent implementation; agents cannot invent the missing decision. Do not create agent fan-out without a concrete role contribution.

The worker must preserve other changes and may not switch branches, commit, or expand ownership unless the brief explicitly authorizes it. On return, apply [dispatch postflight](dispatch-postflight.md).
