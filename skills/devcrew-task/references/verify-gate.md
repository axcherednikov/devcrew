# Verification gate

The package uses explicit local verification helpers instead of hooks. `verify-check --record RECEIPT` validates a recorded command against its output, exit status, timeout state, Git working-tree fingerprint, and log digest. The host project is inferred from the receipt path. For AGENT EXECUTION, pass the expected `--execution-root PATH` and, when available, `--task-id ID`; the receipt and log stay in host checks state while freshness is checked against the task execution root. Wrong expected task/root values fail even when the trees happen to have equal HEAD and fingerprints. Omitting these options preserves single-root verification for legacy records. `wave-gate --project HOST --execution-root TASK [--task-id ID]` validates disjoint normalized ownership, previous-wave completion and integrated check records covering all ordered verification bindings. Declare the bindings from project rules and the accepted plan and approve at wave zero before execution. Later calls always reject changes to the approved plan. Wave-zero `--replan-reason` only reports a request requiring separate trusted reconciliation and never approves or refreshes bindings; text or role names are not authorization. Repeated wave zero with the unchanged plan remains idempotent. Exact argv, timeouts and the inherited environment must match the accepted bindings. Split-root evidence requires the expected execution root. The latest completed wave must match the current execution tree; earlier waves are historical evidence with validated record/log integrity. `review-gate --project HOST --execution-root TASK` requires the exact expected lens set and a `state` captured before review with `capture-state --project HOST --execution-root TASK`. It rejects changed HEAD/files as well as malformed, missing, failed, or unresolved P0/P1 evidence.

Keep machine reports in the configured checks directory. A fresh state object does not substitute for reviewing a changed tree; a successful recorded command does not prove product acceptance without inspecting its output. Formats and compatibility are in the [runtime contract](../../../docs/runtime-contract.md).

No automatic hook is installed or enabled by this package.


## Evidence completeness for negative results

A successful command event proves that the recorded command completed; it does not by itself prove that the intended state or branch was reached. For negative claims, bind a positive witness to the same run and object and name the expected trigger and observable condition. Empty, stale, foreign, missing or truncated evidence cannot establish absence. Distinguish mixed outcomes, stale identity and missing observations when material; do not require every combination. Static evidence may still support a concrete finding. Use targeted mutation checks when risk warrants them rather than requiring mutation for each change.
