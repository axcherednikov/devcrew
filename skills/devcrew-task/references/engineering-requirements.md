# Engineering requirements

Use the configured project memory registry for explicit, durable engineering requirements that must survive independent sessions. The registry is `engineering-requirements.json` under the memory path in `.codex/devcrew.json`; a missing registry is an empty, read-only fast path.

During the current task, assess an explicit user requirement once. First inspect applicable `AGENTS.md`, project rules/docs, configured memory, and the relevant formatter, linter, or static-analysis configuration. If an existing canonical source already owns the requirement, record only a reference to its normalized path and exact fragment plus file and fragment digests. Never copy the instruction into a second durable body. For a genuinely new rule, record its trigger, action, check, selectors, origin, assessment rationale, and evidence. Existing tools are preferred; reference their actual configuration and verification command. A required new check outside the accepted plan returns through the normal planning/replan route.

Use `requirements-record --project HOST --expected-registry-revision N --record JSON` for a structured coordinator assessment. The record must state `assessment.durable: true`, an evidenced `distinct` or `equivalent` comparison, and a current registry revision. Equivalent decisions reuse the canonical ID; distinct decisions get a separate ID. An uncertain comparison stays task-local. One-time requests, unresolved conflicts, unsupported reviewer claims, and arbitrary tool/agent text are not durable requirements. A confirmed reviewer issue needs separate evidence that it is reusable. Replays are no-write; changes revise the same ID with a reason and history digest. Inspect the current registry before selecting an ID or revision.

Before a planner dispatch with a nonempty registry, provide an explicit bounded `requirements_scope` containing declared repository-relative paths and task class. Ordinary dispatch uses `ordinary issue-dispatch --requirements-scope FILE`, where the file contains `{"paths":[...]}`; its canonical paths are pinned for the current planner cycle. Executor and reviewer contexts use only the accepted plan's `OWNED_SCOPE`; replacements and bounded repairs preserve that accepted scope, while a new planner cycle requires a fresh declaration. Legacy empty-registry tasks remain compatible. A consumed legacy dispatch with a nonempty registry but no trusted bounded scope fails closed; preserve its receipts and history, then create a new ordinary task from the original message with an explicit scope. Before a DIRECT edit, independently load the same context with `requirements-context`; refresh after new requirement feedback before the next bounded edit pass. Standalone review loads its own context. The helper reports the selected bytes and entry count and fails closed on overflow or stale source references.

Use `requirements-diagnose` only with a bounded incident file naming the task, route or spawn receipt, role, task class, declared paths, and available check evidence. It reads the persisted issued route and receipt; it does not change requirements or plans. Report only observed delivery and check facts. Leave semantic applicability, ambiguity, priority, conflict, or agent-compliance causes undetermined unless separate agent evidence establishes them. Receiving a requirement does not guarantee that a model follows it, and a filesystem helper cannot control a model already running.
