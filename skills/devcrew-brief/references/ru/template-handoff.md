# template-handoff.md

Шаблон prompt'а для передачи постановки имплементирующему агенту (или текста-сопроводиловки для человека-исполнителя). Закрывает Шаг 8 «подготовить prompt для имплементирующего агента». Заполняется после того, как постановка прошла все проверки Шага 6.5 и чек-лист Шага 7.

Контракт двусторонний: постановка даёт исполнителю проверенные факты и границы; исполнитель возвращает отчёт по `template-implementation-report.md` — без отчёта петля обучения (`../retro.md`) остаётся без входа.

---

Реализуй задачу <TASK-NNN / slug> по постановке.

## Порядок чтения

1. `<path/task-NNN-short.md>` — зачем задача существует (2 минуты)
2. `<path/task-NNN.md>` — что и почему именно так; границы; acceptance
3. `<path/architecture.md>` — где живёт логика, принципы, раскладка файлов
4. `<path/plan.md>` — пошаговый план с каркасами кода; рабочий документ

Перед началом прочитай также (из «Что важно прочитать перед началом» в architecture.md):
- `<путь>` — <зачем>
- `<...>`

## Блокеры

⚠️ <Повтор pre-dependencies из постановки с текущим статусом: «изменения из TASK-IDb есть в текущей ревизии — можно начинать» / «TASK-ID НЕ смержена — не начинай, пока …». Если блокеров нет — «Блокеров нет, можно начинать сразу.»>

## Статус фактов

Упомянутые в постановке интерфейсы, форматы данных и поведение **сверены с кодом проекта** (commit `<hash>` / ветка `<branch>`, дата проверки <дата>). Если реальность разошлась с постановкой (например, ветка уехала) — не подгоняй код под постановку молча: зафиксируй расхождение в отчёте и реализуй по актуальному состоянию кода.

## Правила отступлений

Постановка фиксирует **контракт и границы**; имена / расположение / стиль — твои, в рамках code-standards проекта.

- **Можно без согласования:** имена классов и методов (в постановке — примеры, «или эквивалентное»), внутренняя структура приватных методов, порядок реализации (рекомендация в architecture.md — не закон). Каждое отступление от рекомендованного — строкой в отчёт.
- **Нельзя без возврата к постановщику:** менять границы scope («заодно сделаю и bulk»), реализовывать вынесенное в «Не делается», пропускать acceptance-критерий, менять согласованный контракт (например, формат вывода, публичную сигнатуру или поведение интерфейса), добавлять зависимости сверх указанных в постановке.
- **Серая зона** (нашёл лучший способ внутри scope, постановка не запрещает, но и не предусматривает): реализуй, но пометь в отчёте как «отступление с обоснованием» — это вход для ретро постановки.

## Definition of done

1. Все acceptance-критерии из `<task-NNN.md>` выполнены — пройдись по списку явно.
2. Прогон зелёный: `<команды lint / build / test / e2e из plan.md>`.
3. Заполнен отчёт по `template-implementation-report.md` → положи в `<папка задачи>/report.md`. Без отчёта задача не считается сданной — он вход для улучшения следующих постановок.

## Подсказки при заполнении

- **Порядок чтения** — не «прочитай всё», а маршрут: short даёт рамку, main — суть, plan — руки. Для человека-исполнителя порядок тот же.
- **Статус фактов** — фиксируй commit/ветку, против которых гонялись проверки Шага 6.5. Постановка стареет; исполнитель должен знать точку отсчёта.
- **Блокеры** — со **статусом на момент передачи**, не копипастой ⚠️-блока. «Опирается на TASK-IDb» без статуса заставляет исполнителя выяснять самому.
- **Правила отступлений** — главная секция. Без неё исполнитель либо рабски копирует имена-примеры (anti-pattern №15 в действии), либо самовольно двигает границы. Списки «можно/нельзя» адаптируй под задачу: если контракт API — ядро задачи, подчеркни его в «нельзя» отдельно.

## Чего избегать

- Пересказывать содержание постановки в handoff — он маршрутизатор, не дубликат. Дубль разъедется с файлами при первой правке (тот же класс ошибок, что ловит task-consistency-check).
- Передавать без статуса блокеров и точки отсчёта фактов.
- Опускать требование отчёта «для скорости» — без отчётов скилл слепнет: ретро не получает вход, калибровка оценок невозможна.
