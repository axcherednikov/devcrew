# ADR: порог и содержание

ADR — запись долгоживущего архитектурного решения, а не журнал интервью. Рекомендуй ADR только для выбора с несколькими жизнеспособными вариантами и долгосрочным контрактом или архитектурными границами, если его дорого/рискованно менять либо будущему разработчику будет неочевидно, почему выбран этот путь. Например: search engine, tenant isolation, migration strategy, event delivery semantics, service boundary, стабильная публичная API-модель.

Не создавай ADR для мелких implementation details, очевидных bugfix, имён локальных классов, обычного refactor, временного эксперимента, дешёвого обратимого выбора, решения, заданного conventions, или каждого ответа пользователя. Сначала найди существующие ADR и не дублируй уже записанное решение.

Сам факт архитектурного выбора не означает, что выбор уже сделан. Если пользователь явно подтвердил решение в запросе, его можно записать согласно правилам проекта. Обоснованный внутренний технический выбор в подтверждённых границах делает назначенный planner по [engineering policy](../../../devcrew-task/references/engineering-policy.md#understand-first-choose-the-smallest-complete-solution), фиксируя факты, вывод и основание; архитектурная значимость сама по себе не требует вопроса пользователю. Если остаётся существенное неясное требование, изменение согласованного поведения либо неразрешённый риск для данных, безопасности или необратимых последствий, покажи `DECISION`, `OPTIONS`, `RECOMMENDED`, `TRADE-OFF`, `WHY ADR` и дождись решения владельца до зависимой реализации. Помечай `ADR_RECOMMENDED`; не записывай неподтверждённый выбор как accepted. Статус accepted определяется процессом принятия ADR в проекте, а не уверенностью исполнителя. Если ADR нужен, но решение ожидает подтверждения, статус `proposed` означает предложение, а не утверждённую запись.

Короткий ADR содержит только:

```markdown
# <Decision title>

## Context
<Почему возник выбор>

## Decision
<Выбранный вариант>

## Alternatives considered
- <Реальная альтернатива>

## Why
<Главный rationale и trade-off>

## Consequences
- <Основные положительные и отрицательные последствия>

## Evidence
- <Связанный code/docs/task reference, если применимо>
```

Не включай полный brief, историю обсуждений или implementation instructions. Уважай существующие формат, каталог и процесс принятия ADR в целевом проекте; этот reference не назначает универсальную директорию.
