## Подсказки при заполнении

### Где живёт логика

Это обзор для «новичка в этой области» — даже если исполнитель опытный, эта секция помогает выстроить ментальную карту до погружения в файлы. 2-5 абзацев. Не дублирует структуру файлов, объясняет домены и их взаимодействие.

### Базовые принципы

Не общие («следуйте clean code») — конкретные для этой задачи:
- «Хранилище X — единственная точка связи Y ↔ Z»
- «Сервис домена A не зависит от entity домена B»
- «`branchId` теперь nullable — управляется только через X, не через sync»
- «Если есть существующий интерфейс Y — используем его, не плодим новый Z»

Нумерация — для удобства ссылок («см. принцип 3»).

### Структура файлов

Группируй по логическим разделам, не по алфавиту. Каждый файл с пометкой:
- **NEW** — будет создан
- **UPDATE** — будет изменён
- **DELETE** — удалить (если применимо)

Опиши:
- **Что содержит** — главные ответственности
- **Почему здесь** — почему в этом модуле, не в соседнем
- **Какие связи** — какие зависимости, кто использует

### Иерархия модулей

Ascii-схема показывает, что от чего зависит. Полезна, когда есть нетривиальная инвертированность зависимостей (port-adapter, DI-tokens, и т.п.).

### Что НЕ делаем

Конкретные anti-pattern'ы именно для этой задачи. Не общий список («не пиши плохой код») — а «в этой задаче кажется естественным сделать X, но не делай, потому что Y».

Примеры:
- «НЕ оставлять deprecated-метод `oldMethod` — удалить целиком, не оставлять как fallback»
- «НЕ заводить новый interface — расширяем существующий `IExisting`»
- «НЕ менять сигнатуру `oldMethod` под новые требования — это сломает других потребителей. Лучше новый метод рядом»

### Порядок реализации

Рекомендация, не закон. Полезно, когда есть зависимости между шагами (например, совместимый читатель → обновление формата записи → проверка старых файлов).

### Что читать перед началом

Конкретные файлы, которые помогут вникнуть. Не «весь проект» — а 5-10 ключевых:
- Соседние сервисы по теме
- Образцы стиля, на который равняемся
- Существующие тесты, которые показывают паттерн

## Чего избегать

- Описание реализации (имена классов, точные сигнатуры) — оставь main.md и plan.md
- Принципы в духе «делайте хорошо» — конкретика для этой задачи
- «Структура файлов» как просто список без «почему здесь»
- Иерархия зависимостей в виде «модуль A зависит от модуля B» без объяснения
