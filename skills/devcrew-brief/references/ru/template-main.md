# template-main.md

Шаблон главной постановки — для исполнителя. Технически детально, но без преждевременной реализации. Должна давать чёткое понимание «что и почему», оставляя имена / расположение / стиль на усмотрение разработчика (в рамках code-standards проекта).

Размер: 150-300 строк (для крупных задач — может быть больше).

---

## Подсказки при заполнении

### ⚠️ блоки сверху

- **Pre-dependencies** — конкретно. «Нужен X» — плохо. «Нужен метод `Y.foo(...)` из задачи Z (уже смержена в dev)» — хорошо.
- **Координация** — если задача меняет контракт, который потребляет другая команда / параллельная задача — указать, с кем согласовать
- **Контекст** — если данных нет / есть legacy / есть особенности окружения (нагрузка, прод-ограничения)

### Подразделы «Что делаем»

Выдели области, которые действительно затрагивает изменение. Для интерфейса это может быть действие пользователя и состояние экрана, для библиотеки — публичная операция и совместимость с вызывающим кодом.

### Алгоритмы

Опиши последовательность действий, если их порядок важен. Например, конвертер проверяет входные данные, полностью записывает временный результат и только после успеха заменяет целевой файл. Укажи, что увидит пользователь при ошибке проверки или записи.

### Тесты

Не пиши «юнит на сервис, e2e на endpoint» — это бесполезно. Перечисли конкретные сценарии, особенно edge-cases. Negative-кейсы выписывай отдельно.

### Зачем именно так

Каждое решение, где есть < 2-3 альтернатив — обоснуй. Шаблон:

> **<Решение>.** <Что выбрали.> <Альтернативы, которые рассмотрены и отклонены, с причинами.> <Главный trade-off — что теряем, что выигрываем.>

Это критическая секция — через 3 месяца никто не помнит, почему выбрали так. Без обоснования возникает соблазн переделать.

### Acceptance

Должно быть конкретно. «Тесты зелёные» — слабый критерий. Сильные:
- «Миграция применяется на dev/test без ошибок»
- «При первом запросе X в ответе видно поле Y корректное»
- «Повторный запрос Z — no-op, не создаёт дубль»
- «Существующие e2e тесты не сломались (regression)»

### Не делается

Каждый пункт с указанием куда. Шаблон:
- «<Что>» — <отдельная задача / следующий релиз / out of scope MVP / когда появится требование, заведём>

### Оценка

С раскладкой. Помогает калибровать прогноз и спорить адекватно.

## Чего избегать

- Полная реализация в постановке (имена классов, точные сигнатуры методов, конкретные строки кода) — оставь исполнителю
- Жёсткое предписание имён файлов и каталогов — даём ориентир, не закон
- «Out of scope» без указания куда
- Магические оценки без раскладки
- Пропуск секции «Зачем именно так» для архитектурных решений
- Acceptance в виде «всё работает»
