# template-implementation-report.md

Шаблон отчёта исполнителя после реализации. Заполняет исполнитель (агент или человек), кладётся в папку задачи как `report.md`. Назначение — не бюрократия, а **структурированный вход для `../retro.md`**: секции 2-3 — это готовые к классификации промахи постановки, секция 4 — данные для калибровки оценок.

Размер: 15-40 строк. Пустые секции не удалять — явное «нет» информативно.

---

## Подсказки при заполнении (для исполнителя)

- **Секция 3 — без вежливости.** «Постановка отличная» с замолчанными пятью минутами поиска недокументированного enum'а — хуже, чем честное «неполно: значение enum пришлось грепать самому». Автор постановки использует это для улучшения процесса, не для самооценки.
- **Секция 4 — по той же раскладке**, что в постановке, иначе сравнение невозможно. Если реальная работа не легла в компоненты раскладки — это само по себе находка для секции 3 (раскладка не отражала структуру работы).
- **Секция 5 ≠ секция 2.** Отступление — внутри scope; находка — за его границами. Реализованная находка из секции 5 — нарушение границ, см. handoff.

## Что делает постановщик с отчётом (для автора постановки)

1. Секции 2-3 → прогнать через `../retro.md`: каждый пункт классифицировать (A/B/C/D), внести правки по маршрутам, одиночные C — в `misses-log.md`.
2. Секция 4 → строка в журнал калибровки (когда он появится; до тех пор — в `misses-log.md` отдельной секцией не копить, достаточно факта в отчёте).
3. Секция 5 → завести задачи / дописать в существующие. Не оставлять в отчёте умирать.
4. «Замечаний нет» в секции 3 → тоже зафиксировать мысленно: подтверждение, что пайплайн проверок отработал.
