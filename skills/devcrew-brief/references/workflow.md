# Writing a task brief

Before any full brief, including read-only briefs, confirm the user has already
selected a strong model; ask the owner to choose if unknown or insufficient.
Never override the model automatically or increase cost. For briefs intended to proceed into
execution, including one routed from `devcrew-task` for material uncertainty,
also use the supervised handoff in
[supervised-execution.md](supervised-execution.md). Resolve material owner
decisions before child creation, show the complete brief, and obtain explicit
human approval for creating one visible Codex chat and later in-scope messages.
Until that approval exists, do not create a thread or start execution. Step 8
suggestions remain for ordinary/read-only briefs and do not authorize execution.

## When to use this workflow

- The user asks you to describe a task, write a brief, or prepare a specification.
- The user has an informal idea and wants to give it structure.
- A large task needs to be broken down. Prepare a separate brief for each subtask.
- An existing draft, whether generated by an AI or supplied as a human-authored file such as `draft.md`, needs to be turned into a brief.

## Working principles

1. **Start with sources.** Extract facts and decisions from the request and supplied materials. Ask only for information still needed to establish the requirements. Reuse answers to questions already resolved. See [interview questions](questions.md).
2. **Use language the user understands.** Ask “Who uses this?” and “What should happen?” Use the answers to identify the technical details yourself.
3. **Read the existing code.** Find the domain entities, interfaces, and patterns the task can reuse or might conflict with. Otherwise you may propose something the project already has. See item 2 in [common mistakes](anti-patterns.md).
4. **Set explicit boundaries.** State what is included and excluded. For each exclusion, link to the task that will own it or say that a task will be created when the need arises.
5. **Explain trade-offs.** Give the reason for each architectural decision. Name the alternatives you considered and why you ruled them out.

## Procedure

### Step 1. Understand the request

Let the user describe the idea in their own words. Hear them out before asking follow-up questions on the first turn. Restate what you understood so the user can correct it.

### Step 2. Inspect the repository

Read the relevant domain entities, services, repositories, and interfaces. Check related tasks wherever the project keeps them, using its documented task or issue index. Read architectural and style guidance in `AGENTS.md`, `README.md`, and other project documents.

Identify:

- Existing behavior and components the task can reuse.
- Interfaces the new behavior must implement or extend.
- The boundary between this task and related work.
- Concrete dependencies the brief must name.
- Conflicts with existing work, such as duplicate interfaces or incompatible data models.

If the project has no code yet, skip this inspection and ask about the stack, style, and architecture during the interview.

### Step 3. Interview the user

Determine which parts of the request, documents, and code establish the requirements. If conflicting sources would change the task, ask a focused question. Use [questions.md](questions.md) for material gaps. When several decisions remain open, map their dependencies. Ask only about decisions whose prerequisites are known and whose answers are unavailable in the repository. After each answer, record confirmed decisions, recompute dependencies, drop obsolete questions, and identify newly answerable ones. Group independent questions into the smallest useful round. Continue independent planning while another branch waits for an answer. Use project conventions for details they settle safely.

Cover the goal and user, flow, edge cases and failures, context and dependencies, volume or load, and exclusions as relevant. Ask one or two questions per message, use plain language, and restate the answer to check understanding. Follow up when an answer exposes another material gap.

### Step 4. Derive the technical work

Map each requested outcome to an affected component, its observable contract, any prerequisite and a way to verify it. Discover the entry points in the target repository.

### Step 5. Choose the size and location of the brief

Produce the smallest standalone package that serves the reader. One file can cover a cohesive task. Add a short business summary for a separate audience, an architecture document for significant choices and trade-offs, and a plan for dependent stages that have their own verification. Hours, component counts, and length do not determine the format.

Create a directory inside the configured, Git-ignored task directory, which defaults to `.codex/tasks/<slug>/`. Follow the [project state layout](../../../docs/project-state-layout.md). The brief, plan, draft architecture/ADR, implementation report, and handoff are task working materials. Do not create a `docs/<task>/` directory for these files. Summarize final behavior or an accepted long-term decision in existing `docs/`, a lesson in `memory/`, and a confirmed invariant in `rules/`. Keep the full task package in its working directory.

Use a ticket number where one exists, for example `TASK-XXX/` or `<TICKET>-XXX/`. Otherwise use a descriptive slug such as `bindings-admin-api/` or `staff-branch-membership/`.

### Step 6. Fill in the templates

Use the artifact language the user explicitly requests; otherwise use the user's language. For a Russian-language request, answer in Russian and use the Russian templates unless the user specifies a different language. The default English templates are the `template-*.md` files in this directory. Russian counterparts with the same filenames are under `ru/`. Keep the output filenames and paths the same across languages, including the brief, plan, handoff, and report, so subsequent steps can find them.

- `template-short.md` gives tracker and product readers a business summary.
- `template-main.md` supplies the implementer with the complete technical brief.
- `template-architecture.md` describes file organization and architectural principles.
- `template-plan.md` outlines the implementation steps with code examples.

Replace each `<...>` placeholder with the facts for this task. Remove inapplicable sections, such as POS provider integration tests for a task with no integration.

Mark the sources of material requirements and decisions using the [provenance check](provenance-check.md). A table is enough for a one-file brief. For a larger package, use decision IDs with a shared decision log. Repeating an assumption across several documents cannot establish owner approval.

### Step 6.5. Choose checks according to risk

The main agent normally checks the brief. Before delegating, decide whether one pass and a targeted check can complete the task safely. For a small, unambiguous brief, verify the facts and affected requirements directly. Extra reports, agents, and review waves need a concrete purpose.

1. **API fact-check.** Check the existing APIs mentioned in the brief against the code and reuse established facts. See [fantasy-api-check.md](fantasy-api-check.md).
2. **Provenance.** Verify the source of each material requirement and mark assumptions. See [provenance-check.md](provenance-check.md).
3. **Short brief.** Check for implementation details when there is a separate business-facing `short.md`. See [short-purity-check.md](short-purity-check.md).
4. **Consistency.** Compare contracts and decisions repeated across files or sections. After editing, recheck affected claims. See [task-consistency-check.md](task-consistency-check.md).
5. **ADR.** Read existing decisions. Recommend an ADR for a durable architectural decision with real alternatives. Keep proposed and accepted decisions distinct. See [ADR threshold and format](adr.md).
6. **Design review.** For unresolved material risks in concurrency, money, integrations, or shared contracts, use the [design review](design-review.md). Give a read-only role a bounded question if independent analysis is needed.
7. **Executor dry run.** Use the [dry run](executor-dry-run.md) on the final text for a complex or ambiguous handoff. A read-only agent receives the package without discussion history to check what the implementer will understand. Use a reader for this check and keep the executor role for implementation.
8. **Optional plan critique.** Use [grill.md](grill.md) when a sufficiently formed, non-trivial plan or ADR warrants stress-testing because of a decision or risk, or when the user explicitly requests it. Ask one question per turn using the existing dependency graph. Skip this check when it adds no value. It does not require a separate agent or a new discovery phase.

The individual references give delegation prompts for cases where delegation is justified. Resolve contradictions in the files before delivery. For a complex package, settle the facts and consistency first, then the design, then the dry run if needed. Give a new reader a specific open question rather than repeating a check already done.

### Step 7. Check the brief before delivery

For each applicable item, identify the fact you checked and the result. Self-checks need no separate report. If independent delegation is unavailable or prohibited, use the same criteria for an explicitly labeled self-check and report the limit on independence. A project requirement for independent review remains open until that review takes place.

**1. Verify and resolve the applicable findings from step 6.5.**

- [ ] API claims flagged ✗ or ⚠ have been corrected in the files with actual names, signatures, and enum values. No “implementer will find this” placeholders remain.
- [ ] Material requirements have a verified source or an explicitly stated assumption. No owner decision has been invented.
- [ ] Corrections agree across all affected documents. An independent reviewer received the necessary contract and design.
- [ ] If there is a short brief, implementation details have been rewritten for business readers. Disputed terms confirmed as business vocabulary are in the project's `glossary.md`.
- [ ] For a multi-file brief, scope is consistent across all files. Recheck after scope changes or fixes to design blockers.
- [ ] Where a scenario recurs in one file, consistency check 12 gives it the same observable outcome across the flow, tests, and acceptance. Specify the required property and describe any default mechanism separately (anti-pattern 17).
- [ ] For a design review, blockers are resolved. Accepted risks and the condition for revisiting them are recorded.
- [ ] For a complex or ambiguous handoff that needed a dry run, the reader's questions are answered in the files, and their first step matches the intended order.

**2. Check the details the delegated checks do not cover.**

- [ ] Give each ⚠️ prerequisite a specific task or method name at the top of the document. “Needs the external service” is too vague.
- [ ] Close business questions or flag which product decision is needed before work starts.
- [ ] Give each out-of-scope item a destination.
- [ ] Break down the estimate by component.
- [ ] Compare proposed interfaces, migrations, and entities to the code found in step 2 to avoid duplication.
- [ ] Review the [common mistakes](anti-patterns.md) from beginning to end.

### Step 8. Hand off the brief

After delivery, suggest a next step only if it serves the user. Possible options include:

- Preparing an implementer handoff using `template-handoff.md`: reading order, blockers, baseline commit for verified facts, rules for deviations, and the required report.
- Reviewing the delivered brief if a review skill is available.
- Assigning targeted discovery of the existing codebase.
- Breaking the task down further if it proved larger than expected.

Let the user choose. Suggestions do not start these workflows.

The handoff asks the implementer to write `report.md` in the task directory using `template-implementation-report.md`. The report sections on deviations and errors or gaps in the brief provide structured input for a retrospective. Classify each reported item using `retro.md`.

### Learn from a delivered brief

Feedback may arrive in a later session, even a week after delivery. If the implementer is blocked, review finds an omission, or the implementation diverges because the brief was wrong, follow [retro.md](retro.md). Record and classify the miss (A/B/C/D), fix the brief, save the lesson in the appropriate project location, and rerun the failing case. Record an isolated low-cost type C miss in `brief-misses.md` in the target project's configured memory directory. A second occurrence of the same class warrants a check.

## Writing style

Use the selected language, active voice, and specific statements. Use a calm, matter-of-fact tone. Reserve ⚠️ for warnings and omit decorative emojis. Use Markdown bullets (`- `) for lists and two spaces for nested items. Use code fences for SQL, code, and JSON schemas. Use tables for comparisons and matrices when they help the reader. To compare two or three options, use columns such as Option, Rationale, Alternatives, and Estimate. Let the facts and acceptance criteria determine section length.

## What every brief contains

1. **Title** in the form `<short description> (back|front|fullstack|infra)`.
2. **⚠️ Prerequisites** where the task depends on other work.
3. **Goal** in one to three sentences explaining who benefits and what they receive.
4. **In scope** with the work this task covers.
5. **Out of scope** with the destination of excluded work.
6. **Estimate** broken down by component with uncertainty stated.
7. **Acceptance** expressed as observable completion criteria.
8. **Verification** describing the relevant scenarios and how to confirm acceptance.

Add context where there is relevant history or legacy behavior, rationale for architectural trade-offs, and coordination details when another team or task is affected.

## Common mistakes

See [anti-patterns.md](anti-patterns.md) for examples and the complete list.

1. Putting column names or code in a business-facing `short.md`.
2. Duplicating an existing interface without checking what is already there.
3. Moving work to a follow-up when it belongs in the current task.
4. Excluding work without recording where it goes.
5. Giving an unexplained estimate such as “6 hours.”
6. Leaving business questions open without identifying the decision required.
7. Naming a dependency too vaguely to act on it.
8. Burying a blocking dependency in the text.
9. Supplying mock stubs without a plan for connecting the real implementation.
10. Designing a vendor-neutral port and adapter for a single vendor without an actual second use case.

## Reference files

Read the files next to this workflow in `references/` as needed:

- `questions.md` supplies focused interview questions for step 3.
- `grill.md` describes an optional stress test for a sufficiently formed, non-trivial plan.
- `adr.md` gives the threshold for an ADR, the confirmation rule, and a short template.
- `template-short.md`, `template-main.md`, `template-architecture.md`, and `template-plan.md` are templates to copy into the task directory and fill in.
- `fantasy-api-check.md` explains how to check claimed APIs before the checklist, delegating to a bounded research agent when justified.
- `short-purity-check.md` checks the short brief for implementation details. Use the main agent by default and delegate to a bounded research agent when the risk calls for it.
- `task-consistency-check.md` checks repeated claims across files and sections. A bounded research agent can help in complex cases.
- `design-review.md` explains an adversarial design review by a strong reviewer after applicable first-pass checks. Use it for concurrency, distributed systems, money, TTL, new dependencies, or changes to shared behavioral contracts.
- `executor-dry-run.md` tests whether a fresh reader can understand the final brief without the interview. Run it last, for complex or ambiguous handoffs.
- `template-handoff.md` is the handoff prompt template used in step 8.
- `template-implementation-report.md` structures the implementer's report. Sections 2 and 3 feed the retrospective.
- `retro.md` describes how to classify a miss, correct the relevant material, and run a regression check after an error in a delivered brief.
- `misses-log.md` provides the cross-session log for tracking whether a miss occurs twice.
- `anti-patterns.md` shows common mistakes to look for.

Adapt the templates to the project's actual stack, including its normal entry points, packaging and test commands.

## Project context

First read the applicable `AGENTS.md` in the **target repository**, then `.codex/devcrew.json` if present, the configured project context, and relevant maps. If there is no project context, inspect existing `docs/`, `memory/`, and `rules/`, then use `$devcrew-setup`. Record only repository facts and user answers. Keep state out of the installed plugin directory. Leave unknowns as open questions. Examples do not establish conventions for the target project.

The references illustrate procedures. For a fresh dry run, provide only the brief files and access to the codebase. If the available delegation interface cannot start a fresh context, disclose that limitation and do not present the check as independent.

The retrospective records lessons in `brief-retro.md` under the configured memory directory and corrects the current brief. Changes to the plugin source require a separate maintenance task.
