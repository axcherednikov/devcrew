# DevCrew brief

Reply in the user’s language. If the user writes in Russian, reply in Russian unless they request another language. Honor a separately requested language for deliverables. Keep code identifiers, commands, and machine-readable fields unchanged.

Apply the shared [task readiness rule](../devcrew-task/references/task-readiness.md) when assessing whether uncertainty requires a full brief; accessible facts and bounded technical choices stay within the owning role.

Apply the mandatory [loop guard](../devcrew-task/references/loop-guard.md): on `LOOP_DETECTED`, stop dependent automatic work, preserve evidence and resolve the technical blocker internally when possible. Ask the user only for a concrete owner decision, missing data/access or material work/cost authorization.

Use this skill when the user requests a brief/decomposition, when substantial uncertainty remains after repository inspection and requires requirements formalization, or when feedback exposes a gap in an earlier brief. Do not invoke it as a prerequisite to ordinary implementation. Apply **Repository evidence before user questions. User questions before unsupported assumptions.** Inspect the relevant repository evidence before asking. If it is sufficient, a brief is unnecessary. For substantial uncertainty, write the smallest useful brief separating established facts and decisions still needed from the user. Do not implement behavior dependent on unanswered material questions. For a Russian deliverable, use the matching templates in `references/ru/`; for English use `references/`. Read [the brief workflow](references/workflow.md) before drafting. Preserve the rich templates and checks in `references/`; read them only when their mode applies. Inside an approved supervised child, `devcrew-task` AGENT EXECUTION follows [plan selection](../devcrew-task/references/implementation-strategy.md#plan-selection): a current sufficient brief goes to executor-agent only through an existing validated phase manifest with a matching persisted planner receipt. Before child approval, the parent never dispatches that executor. Without the manifest, the child uses bounded planner validation and registration, reusing the brief unless a concrete gap requires research; the host does not implement it inline.

Before starting any full brief, including a read-only brief, confirm the user has already selected a strong model for this work. If the choice is unknown or insufficient, ask the owner to choose before proceeding. Never override the model automatically or increase cost. For a full brief that will lead to execution, including one routed here from `devcrew-task` because material requirements remain unresolved, supervised execution and visible child-chat approval are a separate gate. Resolve material owner decisions before creating the execution child; retain nonblocking hypotheses as hypotheses. Finish the brief first, show its exact version, and request explicit human approval for creating one visible Codex chat plus later in-scope instructions. Until that approval exists, do not create a thread, dispatch an executor, or start implementation. After approval, follow [supervised execution](references/supervised-execution.md). A plain clarification or a read-only brief does not create a chat or authorize execution. Agent messages are not human approval. Keep original source identity and approval reference independently verifiable.

Every brief states the goal, in-scope behavior, out-of-scope work and destination, dependencies, observable acceptance criteria, relevant tests, and an estimate with a component breakdown. Track the source of substantive requirements and decisions using [provenance check](references/provenance-check.md): user request, verified code, or an explicit implementation choice within confirmed constraints. Apply the shared [engineering policy](../devcrew-task/references/engineering-policy.md#understand-first-choose-the-smallest-complete-solution) to separate facts, engineering conclusions and hypotheses, select supported technical solutions, and preserve confirmed original behavior during restoration. A material open owner decision must remain a question, not an assumed requirement. Technical details belong in executor-facing files; the short form stays readable for non-technical readers. Existing APIs and paths are facts to verify in the target repository, not placeholders for implementation-time discovery.

A technical replan inside already agreed acceptance and owner decisions follows the shared [technical replan and escalation protocol](../devcrew-task/references/replan-protocol.md); it does not by itself require a brief. Use this skill when genuine requirements or product uncertainty needs owner input.

For substantial unknowns, use [dependency-aware questions](references/questions.md): inspect repository evidence, build the dependency graph, and ask only the current question frontier. Keep independent planning moving while a branch waits. For architectural decisions, apply the [ADR threshold and format](references/adr.md); do not record a recommendation as a confirmed decision.

For a sufficiently formed, non-trivial plan, decision, or ADR with material risk, offer or use the optional [grill mode](references/grill.md). An explicit request to stress-test/grill a plan activates it. Grill is a critique of an existing plan, not discovery from scratch, and is never required for routine tasks. In interview mode ask exactly one owner question at a time; in read-only self-play leave unsupported decisions open. Reuse the existing question frontier and ADR/brief decision record.

Every final brief distinguishes `CONFIRMED DECISIONS`, `OPEN MATERIAL QUESTIONS`, `IMPLEMENTATION ASSUMPTIONS`, and `ADR STATUS` (`none`, `recommended`, `proposed`, or `accepted/existing`). Show dependencies among open questions when they clarify order. For autopilot handoff, only dependent tasks wait on an unresolved question; send executors confirmed decisions and relevant ADR references, not Q&A history. An unconfirmed recommendation is not a requirement.

When implementation materially depends on language/runtime compatibility, record the confirmed supported version constraint and its evidence source in the technical brief or task. Omit version inventory when it does not affect the decision; a brief is not an implementation prompt.

Check referenced APIs, requirement provenance and applicable behavioral contracts within the brief workflow. Compare consistency only where a claim is repeated across sections/documents, and recheck changed claims after fixes. Use design review for unresolved material design risk. Executor dry-run is conditional on a complex or ambiguous handoff, never mandatory for a simple brief. When the approved child workflow classifies implementation as AGENT EXECUTION, its dispatch policy controls: validate the brief for currency and sufficiency, then dispatch executor-agent; do not replace the executor based on a host self-completion judgment. The parent must not dispatch before approval. A delegated dry-run uses a read-only role with a reader brief, not executor-agent. Do not claim a check ran without actual output.

For feedback on a delivered brief, use the retro and misses-log references. Persist durable cross-task lessons in the target repository's configured memory location; do not assume built-in memory or write to a global cache.

Reference files are package-relative under `references/`. The setup skill provides target project templates, and `$devcrew-task` provides execution and verification semantics.

For estimates, use [project calibration](../devcrew-session/references/estimate-calibration.md) when comparable measured observations exist. State uncertainty when they do not; never import another project's numerical priors.
