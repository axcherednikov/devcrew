# Estimate calibration

Use local completed observations, never numerical priors from another author's project. Record an estimate before execution; preserve it after execution and record the actual separately. Do not retrospectively invent an estimate to fill the ledger. Missing measurements mean no calibrated estimate is available.

Store one JSON object per line in a project-approved ledger. Required fields: `task` (unique task/slice identifier), `unit` (`hours`, `minutes`, or `tokens`), `coverage` (for example implementation or end-to-end), `estimate_scope`, `actual_scope`, `estimate_model`, `actual_model`, `estimate` (finite positive number), and `actual` (finite nonnegative number). Scope and model labels must describe the actual measurement consistently. Use a stable explicit label such as `human` or a documented model mix where applicable; unknown values are not comparable measurements. Do not mix elapsed time with person-hours or model tokens in the same coverage label. Use consistent identifiers without incidental whitespace.

Run `python3 <plugin>/scripts/devcrew.py estimate-summary --records <ledger.jsonl>`. It rejects invalid or duplicate observations, excludes changed scope/model, and groups comparable rows by unit, coverage and model. The ratio is total actual / total estimate, not a speed claim or an automatic multiplier for every future task. Report count, exclusions and uncertainty. An empty ledger returns empty groups, not invented defaults. Compare similar task kinds manually before applying a group's observations to a new estimate. Keep implementation and end-to-end figures separate; review, integration and waiting costs belong only in the coverage that actually measured them.
