# Native coordination procedure

For a full brief with explicit user approval to create a visible chat and send later in-scope instructions, follow [supervised execution](../../devcrew-brief/references/supervised-execution.md). Before any create/send effect, discover current native schemas and reconcile host, project, local checkout, branch, revision and active writer. Use `list_projects` to verify real project identity and the existing sessions inventory to record the prepared action and approval/source references. Create one child only, resolve the actual thread ID before read/send/wait, and preserve native receipts/cursors. On timeout or resume, correlate action ID, native threads/messages and Git state before retrying. Unresolved ambiguity blocks a dependent side effect; a title or local sent flag is not proof. The synthetic handoff must preserve verifiable original-source and human-approval references. Do not launch a subagent as a substitute, promise continuous polling, or change the owning workflow's model/review policy.

This procedure coordinates user-owned native Codex tasks. For collaboration subagents started with `spawn_agent`, use the shared [agent waiting procedure](../../devcrew-task/references/agent-waiting.md); for operating-system processes, use their process interface.

1. Inventory existing tasks with `list_threads`; inspect only relevant tasks with `read_thread`. If the user refers to an archived task, use the available archived-task discovery tools. Confirm identity and checkout from actual state, not a similar title. Inspect available projects only when selecting a target for explicitly requested task creation.
2. Plan dependencies and ownership. At most one writer per resolved checkout; parallel independent implementation writers require an explicit user instruction and distinct worktrees under the [task checkout policy](../../devcrew-task/references/checkout-policy.md). Without that instruction, serialize tasks in the current working directory. Reserve shared databases, integration environments and other exclusive resources with the same agreed resource directory. Busy resources remain queued; never remove another task's lock or kill its processes.
3. Send a bounded continuation to an identified existing task using `send_message_to_thread` when covered by the coordination request. Inspect the current status first: steering a running task can alter its work. Record request ID and expected response in the inventory and include the ID in the prompt. Before retrying, inspect the destination's recent messages/status for that request. There is no guaranteed transport idempotency; if delivery remains ambiguous, mark uncertain and reconcile instead of resending blindly.
4. Use `create_thread` only when the user explicitly requested a new task. First obtain the real project ID and repository flag via `list_projects`; follow the tool's environment selection rules and user preferences. A setup `clientThreadId` is not a usable `threadId`. Do not pass it to read/send/wait tools; resolve setup through available native state. Ordinary decomposition is not creation authority. Do not create tasks just to evaluate this skill. Subagents within one implementation follow `$devcrew-task` and its active delegation rules.
5. Wait for these native tasks using `wait_threads`, batching up to the tool's supported target limit with per-task cursors and host IDs. Prefer meaningful waits up to 60 seconds, then retain cursors. Use a zero-time snapshot for a direct status request. Avoid repeated transcript reads or narration of unchanged polls. A timeout is not a failed task. A quiet log is not proof of a hung process. Collaboration agents use `wait_agent`, not `wait_threads`.
6. On delivery, check the diff, unassigned changes, integration and concrete acceptance evidence before releasing dependencies. Evidence from another worktree is historical input, not certification of the receiving checkout. Review and execution evidence become stale on relevant changes, including a new commit. Record limitations if tools or files are unavailable; never invent results.
7. Before each authorized external action, inspect current target state and ledger, confirm that the reviewed revision is still the intended one, and ensure another actor has not already performed it. After sending, save the receipt and read back the target state where supported. If a timeout leaves the result ambiguous, reconcile by target/action identity before retrying. Do not assume exactly-once delivery from a local ledger. Ask only when missing authorization or unresolved ambiguity prevents a safe action; do not repeatedly ask for authorization already provided.
8. A request to watch/check later requires the available native automation tool. Use its heartbeat defaults and notify only on meaningful changes unless the user asks for routine updates. Without native automation, state that no background monitoring was started; persist a resumable next action. Do not simulate scheduling with endless waits, hidden subprocesses or invented cron commands. If task tools are unavailable, use accessible project artifacts and clearly report that live task status/control could not be verified.

These procedures coordinate native tasks; they neither add MCP services nor claim a continuously running daemon. Never move, interrupt, archive or change another task's model outside the user's scope. An existing authorization remains valid across resumes, but a materially different target or effect requires clarification.
