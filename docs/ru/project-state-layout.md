# Размещение проектного состояния

[English](../project-state-layout.md)

DevCrew хранит техническое состояние работы в игнорируемой `.codex/`. Долговечные знания остаются в принятых проектом `memory/`, `docs/` и `rules/`; их расположение выбирается после изучения правил репозитория.

## Порядок инициализации

До запуска `init`:

1. Прочитайте корневой `AGENTS.md` и применимые вложенные `AGENTS.md`.
2. Перейдите по указанным в них индексам и правилам, например `rules/index.md`.
3. Осмотрите существующие `docs/`, `memory/`, `rules/`, `.codex/agents/`, журналы задач и соглашения об именовании.
4. Выберите пути долговечных знаний по соглашениям проекта, а технические каталоги задач, сессий и проверок — внутри `.codex/`.
5. Только после этого запускайте `init` с найденными путями.

Если специальных соглашений нет, используются значения по умолчанию:

| Назначение | Путь |
|---|---|
| Контекст проекта | `docs/context.md` |
| Карточки задач | `.codex/tasks/` |
| Снимки сессий, handoff и dispatch/capacity receipts | `.codex/sessions/` |
| Долговечная память | `memory/` |
| Записи и журналы проверок | `.codex/checks/` |
| Конфигурация расположения | `.codex/devcrew.json` |
| Версия проектной интеграции и sync metadata | `.codex/devcrew-state.json` |
| Проектные роли | `.codex/agents/` |

## Рабочие материалы и долговечные знания

Все создаваемые DevCrew материалы конкретной задачи лежат в настроенном каталоге задач, по умолчанию `.codex/tasks/<task-id-or-slug>/`: brief, черновики решений/ADR, plan, task card, implementation report, findings и рабочий handoff. Снимки сессий и coordinator inventory лежат в `.codex/sessions/`, машинные отчёты и полные логи — в `.codex/checks/`. Не создавайте для них `docs/<задача>/` или отдельный корневой `sessions/`.

На значимой границе задачи переносите только подтверждённые знания, полезные после завершения текущей работы:

- `memory/`: переиспользуемый урок с конкретным `TRIGGER → ACTION`, областью применимости и проверяемым источником; одноразовые наблюдения остаются в карточке задачи.
- `docs/`: краткое описание итогового поведения, публичного контракта или принятого долгосрочного архитектурного решения. Обновляйте существующий документ или ADR вместо копирования полного brief/plan/report.
- `rules/`: подтверждённый обязательный инвариант проекта, если он действительно отсутствует в действующих правилах; сохраняйте установленный проектом порядок изменения правил.

Перед записью проверьте существующий документ/индекс и уберите дубли. Храните минимум: факт или решение, причину/условие применения и ссылку на устойчивый источник (код, тест, commit или долговечный документ). Игнорируемый task/session файл не должен быть единственным источником долговечного знания. Не переносите полные логи, историю диалога, промежуточные гипотезы, статусы и списки следующих шагов в долговечные каталоги. `docs/context.md` содержит только подтверждённый контекст проекта; текущее состояние работы относится к `.codex/`. Небольшая задача без нового долговечного знания не требует дополнительных записей.

Этот порядок дополняет существующие [session harvest](../../skills/devcrew-task/references/session-harvest.md) и [memory lifecycle](../../skills/devcrew-session/references/memory-lifecycle.md), сохраняя их требования к доказательствам и применимости уроков.

## Настройка путей

Все пути задаются относительно корня проекта:

```text
python3 scripts/devcrew.py init \
  --project PATH \
  --context rules/devcrew-context.md \
  --tasks-dir .codex/tasks \
  --sessions-dir .codex/sessions \
  --memory-dir memory \
  --checks-dir .codex/checks
```

В примере контекст использует принятое проектом расположение в `rules/`, а технические данные остаются в `.codex/`. Новые варианты технического layout выбирайте внутри `.codex/`. Прежние настроенные пути поддерживаются для безопасного чтения и возобновления; перенесите их через `migrate-state` перед новыми записями.

Выбранные значения записываются в `.codex/devcrew.json`:

```json
{
  "paths": {
    "checks": ".codex/checks",
    "context": "rules/devcrew-context.md",
    "memory": "memory",
    "sessions": ".codex/sessions",
    "tasks": ".codex/tasks"
  },
  "schema_version": 1
}
```

`doctor`, `run-check`, `verify-check` и `flaky-hunt` используют эту конфигурацию. Повторный `init` без новых флагов сохраняет ранее выбранные пути. Попытка передать другой layout поверх существующей конфигурации завершается ошибкой и не переносит файлы автоматически.

## Перенос существующего технического состояния

На спокойной границе работы, без активных writers:

```text
python3 scripts/devcrew.py migrate-state --project PATH --dry-run
python3 scripts/devcrew.py migrate-state --project PATH
```

Команда переносит только настроенные каталоги `tasks` и `sessions`, расположенные вне `.codex/`, в `.codex/tasks/` и `.codex/sessions/`. Содержимое сохраняется без изменения; дополнительные поля `.codex/devcrew.json` и пути context/memory/checks сохраняются. Уже выбранные каталоги внутри `.codex/` остаются на месте. Все источники и назначения проверяются до записи; существующее назначение, symlink или специальный файл блокируют перенос. При ошибке записи выполненные перемещения откатываются. `--dry-run` ничего не записывает. Команда не сканирует произвольные `docs/<задача>/`: рабочую папку brief, не учтённую в конфигурации, переносите отдельно после проверки её принадлежности задаче и сохранения итоговой документации.

Миграция не переписывает evidence, digest или сохранённые review/dispatch payloads: прежние записи остаются историческими. Проверьте ссылки в карточках, manifests и handoff; перед дальнейшей работой получите свежие проверки/dispatch для нового расположения. Сам факт переноса не подтверждает актуальность прежнего PASS. Команда не изменяет Git index и не создаёт commit. Если технические файлы уже отслеживаются Git, отдельно снимите только проверенные технические пути с tracking, сохранив долговечную документацию. Ignore не скрывает уже отслеживаемые файлы.

Plugin version хранится в manifest plugin package; монотонная версия
проектной интеграции хранится отдельно в `.codex/devcrew-state.json`. Plugin
version change без schema migration не требует изменения project files или
commit. Общий [sync preflight](../../skills/devcrew-setup/references/project-sync-preflight.md)
сравнивает schema до основных DevCrew workflows. Sync добавляет отсутствующие
роли, обновляет только безопасно распознаваемые managed роли и записывает
время/версию синхронизации.

State хранит plugin version, project schema, sync timestamp, template и
installed hashes managed roles. Sync обновляет только локальные файлы и
добавляет `/.codex/` в корневой `.gitignore`, только если каталог ещё не исключён действующими правилами Git; Git index
и HEAD не меняются. Поля `sync_commit` и `sync_commit_id` в результате равны
`null`; старые commit ID поддерживаются только для чтения исторического state.
Произвольные custom roles и другие файлы `.codex/` не принадлежат синхронизации.

## Ограничения и сохранность данных

- `init` не перезаписывает пользовательские документы.
- Пути должны быть относительными, не пересекаться друг с другом и оставаться внутри проекта.
- Символические ссылки в управляемых путях не используются для записи.
- Инициализация сначала проверяет все назначения и только затем создаёт файлы.
- `init`, `sync` и `migrate-state` проверяют исключение каталога `.codex/` через Git: учитываются `.gitignore`, `.git/info/exclude`, глобальный ignore и порядок отрицаний. Если каталог уже исключён, корневой `.gitignore` не создаётся и не меняется независимо от положения правила. Если исключения нет или оно отменено, добавляется `/.codex/`. Ошибка проверки Git останавливает зависимую запись; вне Git сохраняется проверка завершающего локального правила. Проектная `.codex/` остаётся untracked; не используйте force-add для её содержимого. Уже отслеживаемые технические файлы снимайте с tracking отдельно, сохраняя их на диске; sync не изменяет index и не переписывает историю.
- Каталог проверок исключается из отпечатка рабочего дерева, независимо от выбранного пути.
- Роли создаются отдельно в `.codex/agents/`; для их загрузки нужна новая задача Codex.

## Состояние QA-сессии

Локальные профили QA и неизменяемые снимки сценариев хранятся в подкаталоге
`qa/` настроенного каталога задач. Неизменяемые результаты запусков,
подтверждающие материалы и индекс для поиска хранятся в подкаталоге `qa/`
настроенного каталога проверок. Для путей действуют те же проверки безопасности
относительно корня проекта, что и для остальных рабочих данных. Идентификатор
запуска определяет имена его снимков и подтверждающих материалов. Индекс служит
для поиска. Перед выдачей результата отчёт проверяет сам результат, подтверждающие
материалы, снимки, идентификатор проекта и контрольные суммы. Для подтверждения
текущего статуса PASS одной записи о прошлом успехе недостаточно.

Записи о принадлежности и восстановлении управляемых QA-окружений хранятся
в `qa-environments/runs/` внутри настроенного каталога проверок. Там же,
в каталоге проверок, находятся индекс резервирования ресурсов и портов и
блокировка допуска к запуску. Запись хранит путь и контрольную сумму профиля,
намерение запустить окружение, проверенные идентификационные данные процессов,
результаты подготовки и очистки, адреса проверки готовности, сведения о данных
запуска и ошибки очистки. Процесс идентифицируется по времени запуска, группе
процессов и сеансу, поэтому повторная выдача PID другому процессу не приведёт
к его ошибочному распознаванию как исходного сервиса. Запись со статусом
`READY` или `CLEANUP_FAILED` должна содержать все перечисленные поля с теми
типами, которые использует механизм записи. Если поле отсутствует, пусто или
имеет неверный тип, операция прерывается до записи состояния, удаления данных
или отправки сигнала. Порт проверки `ready` также резервируется в индексе,
чтобы его не занял второй запуск DevCrew. Запись запуска хранит его в
`port_claims`, а индекс указывает вид резервирования. Блокировка запуска
в `qa-environments/locks/` обеспечивает последовательное выполнение операций
старта и остановки этого запуска. Блокировка индекса ресурсов проекта
удерживается лишь на время чтения и записи сведений о резервировании.

Записи о подготовке и предусмотренной профилем очистке также хранят группу
процессов, созданную для каждой команды. Записанный результат считается
окончательным, пока в этой группе нет процессов. Оставшиеся дочерние процессы
и их потомков завершают, если связь группы с подтверждённым процессом-лидером
всё ещё можно установить. В противном случае результат получает статус
`EFFECT_UNKNOWN`, а ресурсы остаются зарезервированными. Если текущие
идентификационные данные лидера прочитать невозможно, сигнал ему не отправляют.

Команды очистки из профиля запускаются только после подтверждения принадлежности
данных либо после того, как подготовка или запуск сервиса могли привести
к побочным эффектам. Если операция прервалась раньше, команды очистки
не запускаются. Сбой команды до создания её процесса считается не имевшим
побочных эффектов. Команды очистки выполняются в порядке, указанном в профиле.
Каждая запись хранит порядковый номер команды для восстановления. При каждой
остановке непосредственно перед запуском очередной команды очистки система
заново проверяет сохранённый путь к данным. Это касается и случая, когда
после предыдущего отказа запись о данных осталась в состоянии `EFFECT_UNKNOWN`.
Подмена каталога или символическая ссылка на месте родительского каталога
блокирует и команды очистки, и встроенное удаление. Состояние уже начатого
шага очистки сверяется при каждой остановке, даже если каталог данных уже
удалён. При сохранённой ошибке или неизвестном результате резервирование
остаётся в силе.

Профиль может задать `data_dir` относительно корня проекта за пределами
каталога проверок. При запуске система фиксирует намерение создать каталог
до его создания. Принадлежность каталога подтверждается только после записи
маркера `.devcrew-qa-owner.json` с идентификаторами запуска и проекта.
При остановке система переименовывает помеченный каталог перед удалением.
Если маркер не совпадает, каталог остаётся на месте. Одного намерения без
подтверждённой принадлежности недостаточно ни для удаления данных, ни для
запуска команд очистки из профиля.

При остановке перед удалением сохранённый путь заново проверяется по текущей
структуре проекта. Если он ведёт за пределы проекта, внутрь каталога проверок
или проходит через символическую ссылку, данные остаются на месте и система
сообщает о незавершённой очистке. После переименования запись хранит стадию
ожидания удаления и новый путь, пока каталог не будет удалён. При повторной
остановке система повторяет удаление по новому пути, даже если исходный путь
уже отсутствует. При записанном намерении запуска, результате `EFFECT_UNKNOWN`,
ошибке очистки или неподтверждённой записи о данных ресурсы остаются
зарезервированными до вмешательства оператора. Новый запуск не принимает под
управление чужой процесс и не снимает нерешённое резервирование. Используйте
`qa environment-status` для просмотра состояния и `qa environment-stop`
для освобождения ресурсов. Остановка затрагивает лишь процессы с подтверждённой
принадлежностью, помеченные данные и связанные с ними резервирования.

Попытки веб-проверок, выполненные агентом, хранятся в `qa-web/runs/` внутри
настроенного каталога проверок. Рядом находятся `index.json` и блокировка
допуска. Снимки сценария и профиля хранятся по настроенному пути
`tasks/qa/snapshots/RUN_ID/`. Запись попытки содержит токен запуска, заданные
размеры области просмотра и наблюдения для каждого размера, ожидаемые
и фактические значения проверок, снимки экрана в формате PNG с контрольными
суммами и размерами, статус повторного чтения данных из бэкенда, логические
признаки совпадения значений по полям и результат очистки связанного управляемого
окружения. Снимки экрана копируются в каталог запуска без перезаписи.
Отсутствующие, изменённые или неподходящие по размеру изображения не могут
подтвердить `PASS`. Веб-проверка привязана к сохранённому идентификатору запуска
окружения и при старте требует статуса `READY`. При записи результата система
сначала заново читает данные из бэкенда, затем останавливает это окружение
и требует подтверждённого статуса очистки `STOPPED`. Поиск запусков, вывод
списка и чтение отчёта не требуют блокировки и не создают файлов, поэтому
работают и с материалами, доступными только для чтения.

Каждая попытка повтора получает собственный каталог запуска и отдельный снимок
сценария. Исходный запуск доступен только для чтения. Перед повтором система
заново проверяет проект и текущее состояние привязываемого окружения. Для
повтора нужно другое окружение того же проекта. Идентификационные данные
процессов должны совпадать с записями для каждого сервиса, а базовый URL —
с одним из сохранённых адресов проверки готовности. Если запись `READY`
устарела, сервис завершился, адрес принадлежит другому окружению или окружение
уже привязано к другой попытке, повтор прерывается до создания запуска.
Связь с окружением записывается вместе с каталогом каждой новой попытки,
включая обычный запуск, поэтому даже незавершённая попытка сохраняет своё
окружение. Новые результат и подтверждающие материалы содержат сведения
о происхождении в `replay` — исходный запуск, его контрольные суммы и статус,
параметры выбора и признак изоляции. Индекс проекта хранит `replay_of` для
поиска повторов. Список дефектов строится по сохранённым неуспешным проверкам
и результатам повторного чтения данных. Отдельной редактируемой истории
дефектов нет. У незавершённого исходного запуска нет контрольной суммы
результата. Его можно повторить только с явно заданной изоляцией.
